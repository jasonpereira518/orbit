# Orbit production-readiness audit

**Date:** 2026-09-15 · **Commit audited:** `33a213c` (origin/main, the commit production serves) · **Auditor:** Claude, at Jason's request

**Verdict: not ready for external users yet, but close.** The engineering foundation is unusually solid for a side project: every route handler and server action is tenant-scoped, the deploy gate and schema reconciliation work, security headers are in place, rate limits fail closed, and the core loop (capture → review → contact → chat) is genuinely good. What blocks a launch is a short list of things that would harm or embarrass a real user: there are **no working backups**, account deletion **keeps the user's identity and encrypted keys**, the privacy policy **describes controls that no longer exist** and lacks a disclosure Google requires, refunds **never revoke access**, a rollback **pages you and stops every background job**, and two paths can spend a user's AI key or send real email without bounds or consent.

Most of section A is one to three days of work. Section B is real risk a small invited group can survive if you watch it. Section C is polish.

How to read the labels: **Verified** means I reproduced it (browser, curl, GitHub, Vercel API) or read the exact lines. **Source** means read in code but not executed. **Inferred** means reasoned from verified pieces, with the gap named. **Dashboard** means only checkable in a Vercel, Neon, Stripe, Clerk, Google or GitHub setting I cannot see.

## 2. What is in good shape (so the fixes below are scoped correctly)

- **Tenancy.** Every route handler and server action touching the database goes through `requireUserId` (or the admin/API-key/internal gates) and scopes queries by `user_id`; the four hybrid-search arms are tenant-filtered; id-taking mutations carry a user conjunct. Two exceptions are in A8. (Verified by the authz pass, coverage listed in its report.)
- **Public surface.** Unauthenticated calls to `/api/extension`, `/api/mcp`, `/api/v1` get JSON 401s; token routes (scan, calendar, unsubscribe, MCP URL) use 256-bit CSPRNG tokens, shape-check before any query, and the scan token is hashed, single-use and ten-minute. Internal job routes are fail-closed on `CRON_SECRET` (prod answers 401). Admin routes 404 to non-admins. (Verified: curl, prod.)
- **OAuth CSRF.** All three OAuth flows bind `state` to the session in an httpOnly cookie and re-check the user on callback; denied/missing/bad-state callbacks redirect with a reason and a friendly toast. (Verified: curl + source.)
- **Secrets at rest.** BYOK keys and OAuth tokens are AES-256-GCM with a production-enforced 32+ char secret; keys never round-trip to the client, never appear in an error string, and Gemini auth is header-based so no URL can carry a key. Sentry has `sendDefaultPii: false`. On Vercel the server-side env keys are dead by construction: production is BYOK-only. (Source.)
- **Deploy gate and schema.** `check:env && db:migrate && next build` fails a deploy on a missing production variable or a failing DDL statement; `schemaCoverage()` runs even on a burned version number and catches missing columns/indexes; the reconcile sweep takes a lease. CI on `main` is green and runs typecheck, lint, build and 121 PGlite smoke scripts. (Verified: GitHub.)
- **Headers.** HSTS (2y, subdomains), nosniff, `X-Frame-Options: DENY`, referrer policy, a permissions policy, and a CSP (still report-only, see B12). (Verified: prod headers.)
- **Stripe basics.** Raw-body signature verification, fulfilment from signed metadata / `client_reference_id`, idempotent Lifetime grant, cash bookings keyed by object so double events cannot double-book. (Source.)
- **Product quality.** Capture extracted three people correctly in ~40 s, flagged the existing contact ("Already in your network → Update Sarah / Create new"), marked a guessed field, and derived a reminder from "next week". Chat answered a company question with dated evidence and drafted follow-ups in ~10–15 s. Empty states, the no-key notices and the delete dialog are clear and honest. (Verified: browser.)

## 3. Findings

### A. Launch blockers — fix before any external user

**A1. There are no backups, and nothing said so.** Verified. The `backup` workflow has failed on every run it has ever had (Sep 6, Sep 13, Sep 14). The logs show both GitHub secrets are empty: `age: error: unknown recipient type: ""` and `pg_dump` trying a local socket because `DATABASE_URL` is blank. `.github/workflows/backup.yml` has no failure step and the ops sweep has no backup condition, so the only recovery today is Neon's free-tier point-in-time window (about six hours, per the runbook). *Why it matters:* a corrupted table or a bad migration noticed the next morning loses every user's contacts for good. *Fix:* set `DATABASE_URL` and `BACKUP_AGE_PUBLIC_KEY` as repository secrets, run the workflow by hand, confirm an artifact exists, then do the restore drill from `docs/RUNBOOK.md` into a Neon branch and write the date and duration into the runbook. Add an `if: failure()` step that posts to `SLACK_OPS_CRITICAL_WEBHOOK_URL`, and have the ops sweep open `backup.stale` when the newest artifact is older than 36 h. Half a day.

**A2. Deleting your account keeps your identity, your encrypted API keys and your Stripe customer id.** Verified in source. The Clerk `user.deleted` webhook calls `purgeUserData(userId)` with no options (`src/app/api/webhooks/clerk/route.ts:99-102`), and the default is `keepSettings = true` (`src/lib/user-data.ts:525`), which deletes and re-inserts `user_settings` with `PRESERVED_SETTINGS_COLUMNS`: email, first/last name, avatar URL, all seven `*_api_key_encrypted` columns, `stripe_customer_id`, attribution and more (`:437-478`). The person stays in the admin roster by name and email, forever, with live credentials for third-party providers. The privacy policy promises "real deletion". *Fix:* pass `{ keepSettings: false }` from the webhook and the admin hard-delete path; add a smoke assertion that `user_settings` has zero rows for the fixture user after a webhook-style purge. One hour.

**A3. The privacy policy misdescribes the product, and lacks a disclosure Google requires.** Verified on production. `/privacy` says the operator console shows "counts, plans, usage totals … not the people in your network", that a contact can be revealed "only with a written reason that is recorded in an audit log", and that "there is no reveal-everything switch". In code the reveal gate was removed deliberately (`src/lib/admin-user-detail.ts:33-40`); contact notes and interaction text are read plainly on `/admin/users/[userId]/contacts/[contactId]`; the audit log gets one reason-free `account.view` row per hour (`src/lib/admin-operations.ts:108-160`); and `mintSignInLink` (`:177-201`) is a sign-in-as-any-user switch. Also missing or wrong on the live page: the **Google API Services User Data Policy "Limited Use" paragraph** (required verbatim for `gmail.readonly`, `gmail.send`, `contacts.readonly`, `calendar.readonly`; without it the OAuth app cannot pass verification and stays in test-user mode); the sentence that photos are "then discarded" (they are kept, and the policy says so two bullets earlier); "never sends mail content to an AI provider" (true for event discovery, false for the recruiter scan, which sends candidate bodies to the user's model); no mention of the recruiter scan or the shared recruiter directory; Sentry, Slack, unavatar, Microlink and Gravatar absent from the processor list; and the Terms still say subscriptions run through Clerk billing. *Fix:* rewrite the operator-access section to say what the console can see and that operator sign-in-as-user exists and is logged (or restore a reason-gated grant and log the contact id per reveal, and add `note_batches.source_text`, transcript text and capture photos to `NEVER_REVEALABLE`); add the Limited Use paragraph and a per-scope purpose table; fix the photo sentence; describe the recruiter scan and the opt-in shared directory; list every processor; update the Terms. One day plus a legal read.

**A4. Refunds and lost disputes never revoke access.** Verified in source. `charge.refunded` and `charge.dispute.closed` return `mirror: null` (`src/lib/billing-stripe.ts:593-638, 674-704`), so a refunded Lifetime keeps Lifetime forever and a charged-back Pro keeps Pro until the subscription itself lapses. *Fix:* on a full refund of a `cs:` Lifetime charge, null `lifetime_purchased_at`; on a lost dispute or a refunded subscription invoice, set status `canceled` with `periodEnd = now`. Add a smoke case. Three hours.

**A5. A rollback pages you and switches every background job off.** Verified in source, chain inferred. `/api/health` treats `recorded !== SCHEMA_VERSION` as `schema_mismatch` → 503 (`src/lib/health.ts:120`). Promoting an older deployment therefore fails the uptime monitor, and `ops.yml` gates the sweep, the stalled-import job, the webhook drain and the connector sync on the health probe succeeding. Then the old code's runtime reconcile re-runs its sweep inside a user request and `recordSchemaVersion` writes its own *lower* number (`src/db/index.ts:1806-1817`). The runbook's "promote the last good one" instruction does not mention any of this. *Fix:* health treats `recorded >= SCHEMA_VERSION` as ok (report the mismatch as `degraded`), `recordSchemaVersion` uses `GREATEST(version, EXCLUDED.version)`, and the runbook says what a rollback does. Two hours.

**A6. One import can spend hundreds of dollars of a user's AI key overnight, silently.** Verified in source. The LinkedIn timeline backfill issues one completion per contact with messages on the user's *configured* chat model (not the fast tier), self-continuing under a time budget with no count cap, no spend cap, no opt-in and no notice (`src/lib/linkedin-timeline-events.ts:104-120`, `src/lib/linkedin-timeline-backfill.ts:184-301`, kicked hourly by `process-stalled`). A 10,000-conversation messages export is roughly $10 on Gemini Flash, ~$90 on GPT-4o, ~$100 on Sonnet 4.5, ~$500 on Opus. There is no per-user spend view or cap anywhere; `usage_events` is admin-only. *Fix:* route through `speed: "fast"`, cap contacts per day, skip threads under two messages, show "Deriving timeline for N contacts, est. cost" on the import page with a toggle. Four hours. Then a 30-day cost card in Settings from `usage_events` (B8).

**A7. Fake prospects with invented emails at real companies can be emailed from Orbit's domain.** Verified in source. Without an Apollo key, `searchPeople` returns fabricated prospects and `mockDomain` uses the model-guessed real domain (`src/lib/apollo.ts:309-314`), giving addresses like `alex.chen@capitalone.com`. They are persisted as `status: "selected"` and neither `sendOutreachMessageAction`, `bulkSendOutreach` nor the quality check looks at `enrichment.demo`. Lifetime users have hosted sending but not hosted enrichment, so this is exactly their path. Bounces at real domains damage the sending domain; a catch-all delivers. *Fix:* refuse to send when `prospect.enrichment.demo === true`, never persist demo rows as selected, and make `mockDomain` always `.example.com`. Two hours.

**A8. Two cross-tenant reads.** Verified in source.
- *Recruiter pool.* `recruiters` is a global table with no owner. `logRecruiter` links any caller to an existing row by id, or by name + firm, and `toPublicRecruiter` unlocks `email`, `phone` and `linkedin_url` for anyone holding a link (`src/lib/recruiters.ts:79-97`; `src/actions/recruiters.ts:160-221`), regardless of whether the contributor turned sharing on. A Gmail scan writes the sender's email onto the shared row automatically. Another user can also fill empty PII fields on a row you rely on (`mergeRecruiterFields`), and `sendRecruiterDrafts` mails whatever email is on the row. The recruiters page copy ("Never shared: … anything Orbit read from your inbox") does not match. *Fix short term:* unlock PII only when the row is pooled or the viewer's own link carries it; refuse PII merges from non-sharing callers. *Fix properly:* move PII to `user_recruiter_links`. Half a day.
- *Outreach preview.* `previewBulkSendQuality` loads `outreachMessages` by `inArray(id)` with no campaign or tenant conjunct (`src/actions/outreach.ts:1135-1157`); with a leaked UUID it returns a victim's prospect name, subject and body facts. *Fix:* filter on `prospect.campaignId === input.campaignId`. Thirty minutes.

**A9. A rejected BYOK key is reported as a missing key, and keys are never checked on save.** Verified in the browser. Saving `AIzaSy-INVALID-…` produced "AI settings saved" and "Status: Your key is saved" with no provider call (`src/actions/settings.ts:191-261`). Asking a question then failed with the toast "Add your AI API key in Settings to use this" and the question bounced back into the composer, because `streamText`, transcription and embeddings bypass `aiProviderErrorMessage` and the raw Gemini/OpenAI "API key not valid" body matches the *missing-key* regex. Voice capture does the same and hides the mic button. Embedding failures are swallowed everywhere, so search and chat degrade to keyword-only with no signal and the model then says you don't know anyone like that. *Fix:* on save, make one cheap provider call (`models.list` / `models.get` / `count_tokens`) and show its verdict; add a distinct "X rejected your key" template; wrap the three bypassing paths in the same catch as `completeJson`; surface `pending_embeddings` and the last `error_kind` as an account alert. Half a day.

**A10. Commercial use on Vercel Hobby.** Verified: the team plan is `hobby` (Vercel API) and `/upgrade` takes live Stripe payments. The prior plan named this as an accepted risk; it is still the one item that can cost the deployment. Pro also removes three workarounds the codebase carries (one cron a day, one-hour logs, no queue). *Fix:* upgrade before the first paying stranger. $20/month.

**A11. Production outbound mail was being rejected.** Verified in Vercel runtime errors (Sep 7–9): `[interest-list] Resend rejected the welcome email … "The gmail.com domain is not verified"`, meaning `RESEND_FROM_EMAIL` in production was a gmail.com address, so every waitlist signup got no email and nothing alerted. Whether it has since been changed is a dashboard question. Also verified in source: hosted outreach mail is sent `from: RESEND_FROM_EMAIL` with **no `replyTo`**, so a recruiter's reply lands in Orbit's inbox, not the user's, and a user's own Resend key would still send from Orbit's (unverified-for-them) domain (`src/lib/outreach-send.ts:42, 109-115`). *Fix:* point `RESEND_FROM_EMAIL` at a verified domain, add an `error_events` + ops condition for `resend.rejected`, set `replyTo` to the user's email, and let BYOK users set a verified `from`. Two hours.

### B. Should fix soon — real risk, survivable for a small invited group

**B1. An expired session makes chat fail silently.** Verified with curl. A POST to `/api/chat` without a session is 307'd to `/sign-in`, `fetch` follows it, and the client receives the sign-in page as `text/html` with status **200**. `chat-stream-client.ts` checks `res.ok`, then parses HTML as SSE and gets nothing; the user sees a spinner that never resolves. Server actions get a 307 too. *Fix:* in `proxy.ts`, return `NextResponse.json({error:"unauthorized"}, {status:401})` for `/api/*` instead of redirecting; have the stream client check `content-type`; on 401, show "Signed out. Sign in again" with a link. Two hours.

**B2. Stripe fulfilment has no fallback and no ordering.** Source. `success_url` carries no `session_id` and there is no `checkout.sessions.retrieve` anywhere, so if the webhook is delayed or the handler 500s the buyer sits on the free plan (the celebration watcher polls for 60 s, then gives up) until Stripe's retries land. `customer.subscription.*` events write status blindly with no `event.created` comparison, so an out-of-order `updated` after `deleted` re-grants Pro; `webhook_deliveries.event_id` is not unique, so the mirror path has no event-id dedupe; the MRR ledger can tear on a retry after a mirror write. `stripe_customer_id` has no unique index. *Fix:* append `session_id={CHECKOUT_SESSION_ID}` and verify server-side on `/settings?upgraded=` by replaying through `decideStripeEvent` (the pure module already supports it); store the last applied `event.created` per subscription and skip older events; make the delivery insert `ON CONFLICT (source, event_id) DO NOTHING` and short-circuit. One day.

**B3. Deletion is neither resumable nor reconciled, and grants are never revoked.** Source. `purgeUserData` is a sequential loop over neon-http with no transaction and no ledger; a mid-way throw in the Settings path is a generic toast. A missed or repeatedly failing `user.deleted` webhook (rotated `CLERK_WEBHOOK_SIGNING_SECRET`, outage beyond Svix's retry window) strands every row, including Gmail/Outlook refresh tokens, and nothing compares `user_settings` to Clerk. Disconnecting Gmail/Outlook deletes the row but never calls the provider's revoke endpoint, so the grant stays live in the user's Google account. Contact avatars are written to a **public** Blob path `avatars/<contactId>.jpg` with no random suffix and are never deleted on contact delete, merge or purge (latent until `BLOB_READ_WRITE_TOKEN` is set). Third-party PII from a user's Gmail persists in the shared `recruiters` table after they delete everything. *Fix:* record a purge run and re-run it from `process-stalled` until the footprint is zero; a daily sweep that purges rows whose Clerk user is gone; best-effort revoke on disconnect and in the connections purge step; private/random-suffix avatars deleted with the row; delete recruiter rows whose only links were the departing user's. Two days.

**B4. `/knowledge` loads every contact, full width.** Source. `getKnowledgeBase` runs `db.query.contacts.findMany({ where: userId })` with no column projection and no limit (`src/actions/knowledge.ts:56-59`), pulling `notes` and base64 `profile_image_url` for the whole account and slicing to 400 in JavaScript. This is the exact shape that produced the 60-second timeouts the prior plan spent a phase removing from the dashboard, and the page-budget smoke does not cover this page. *Fix:* project the columns it renders, `ORDER BY updated_at, id LIMIT 400`, add it to `smoke-page-budgets`. Three hours.

**B5. OAuth lifecycle gaps.** Source, one part verified in the browser.
- The single Google grant requests all six scopes (`gmail.readonly`, `gmail.send`, `userinfo.email`, `contacts.readonly`, `calendar.readonly`, `openid`) even when the user came to import contacts (verified: the authorization URL). Google's consent screen will show "send email on your behalf" to someone who wanted their address book. Request scopes per entry point with incremental consent.
- No probe for `gmail.readonly`: a user who unticks mail on Google's granular consent gets "Gmail connected", the scan then fails with Google's raw JSON rendered in the panel, and a missing `scope` in the token response would be recorded as *all* scopes granted.
- Every successful token refresh calls `upsertGmailConnection`, which resets `sync_failures`/`sync_error`/`next_sync_at`, so calendar-sync backoff never converges and a disarmed row is re-armed by any Gmail action (`src/lib/gmail.ts:286-291, 389`).
- When calendar sync does disarm, nothing user-facing reads `sync_error`; the card still says "Connected". `needs_reauth` renders as "Not connected"; only the bell says "expired".
- Eventbrite OAuth outcomes (`?eventbrite=connected|error`) are never read by any component: cancel, "no organization" and token failure look identical to nothing happening.
- Microsoft `interaction_required`/`consent_required` refresh errors are classified as transient, so an Outlook row stays `active` and fails forever with no alert.
- Google People and Calendar calls bypass the retry/timeout wrapper; `fetchGmailHeaders` returns `null` on a 401 mid-job, so a page of expired-token failures counts as scanned.
*Fix:* scope-per-entry-point; a `hasGmailReadScope` probe checked in the callback; split "store refreshed token" from "re-arm on reconsent"; surface `sync_status`/`sync_error` on the connection card and a `connection.google_calendar` alert; read the Eventbrite params like the Gmail panel does; widen the reauth regex; route People/Calendar through the retry wrapper. Two days.

**B6. Alerting has blind spots.** Source. If `SLACK_OPS_WEBHOOK_URL` is unset, delivery throws before the condition is persisted, so `/admin/health` shows nothing (`src/lib/ops-notify.ts:47-48` → `ops-sweep.ts:229-235`). `cron.failed` fires only on `failed`/`stale`, never on a nightly that ends `partial` every night. Embedding and timeline backfill exceptions are swallowed in `after()` with no row anywhere; capture-job failures are rows only. `statement_timeout = "0"` is reported in the deep health view but never alerted. Nothing reads the outbound webhook drain's `cron_runs`. An unattributed Stripe fulfilment is a `console.error` in logs that expire in an hour and `ignored` never trips the streak. `SLACK_OPS_CRITICAL_WEBHOOK_URL` and `BETTERSTACK_HEARTBEAT_URL` (the only detector for a dead scheduler) are not in `EXPECTED_IN_PRODUCTION`. *Fix:* persist alert state before delivery; alert on N consecutive `partial` runs and on `drain.failed`; a throttled `backfill.failed` error source; a `config.statement_timeout_unbounded` condition; record `missing_user_id` fulfilments as error events; add the two variables to the expected list. One day.

**B7. Migration hardening.** Source. `applyScaleSchema` runs `ALTER TABLE contacts DROP COLUMN IF EXISTS linkedin_slug` and re-adds it on **every** version bump (`src/db/index.ts:1455-1461`), a full rewrite of `contacts` under an exclusive lock while the previous deployment is still serving. The version-collision guard covers only columns and named indexes declared in `schema.ts`; data statements in `alters` (the embeddings dedupe `DELETE`, `DROP INDEX`, generated-column expression changes) are silently skipped by a burned number, which the changelog says has happened at 33, 44, 46, 53 and 54. `npm run db:push:DANGEROUS` reads `.env.local` (which in the main checkout carries the remote Neon URL) with no environment guard, and would compute DROPs for `embedding_vector`, the HNSW index and the migration tables. The reconcile lease never fails closed, and its three-minute wait exceeds the 60 s page `maxDuration` if it is ever taken at runtime. Local PGlite has no pgvector, so no pgvector arm or HNSW query ever runs in dev or CI. *Fix:* guard the `linkedin_slug` rewrite with a `pg_get_expr` check; record a hash of the DDL text alongside the version; refuse `drizzle-kit push` unless `ALLOW_DRIZZLE_PUSH=1` and the host is not `PRODUCTION_DB_HOST`; cap the runtime lease wait at ~20 s; run the pgvector smoke against a Neon branch in CI. One day.

**B8. AI layer correctness and cost.** Source; the API reference used by the audit says the `claude-opus-4` preset (`src/lib/ai-providers.ts:48`) is not a valid model id (the aliases are `claude-opus-4-0` / dated), so every Anthropic user who picks it gets "That Anthropic model isn't available" on every feature: verify with a `models.list` call and replace. Anthropic calls always send `temperature`, which newer models reject. Quota exhaustion (`insufficient_quota`, `RESOURCE_EXHAUSTED`, "credit balance") is classified as "give it a moment", the wrong next action. The Gmail recruiter scan treats a rejected key as per-sender failures, completes, and advances the watermark, so those messages are never rescanned. Meeting chunks retry six times per chunk on a quota-dead key. Streaming chat ignores client disconnect. Switching provider keeps the old key active for embeddings and transcription with no per-provider clear. `process-stalled` runs hourly (GitHub) and daily (Vercel) while comments say daily. No user-facing usage view or spend cap (see A6). *Fix:* the model id; omit `temperature` for Anthropic; a `quota` error kind with "top up at X" copy; abort the scan on an auth/model error before advancing the watermark; terminal codes for auth/quota/model errors in the chunk route; wire `request.signal` into `streamText`; per-provider clear buttons; a 30-day cost card in Settings and a soft daily token cap that pauses background jobs. Two days.

**B9. Terms acceptance and self-service account deletion.** Source. `<SignUp>` renders no consent element; acceptance is browse-wrap unless Clerk's "require express legal consent" is on (dashboard). The policy says you can "delete your account entirely" from Settings, but the only path is Clerk's account portal (and see A2). *Fix:* enable the Clerk consent requirement and record version/time on `user.created`; add a real "Delete my account" in Settings that purges with `keepSettings: false` and then deletes the Clerk user. Half a day.

**B10. Export and per-contact deletion are incomplete.** Source. Export covers six tables (contacts, interactions, reminders, tags, imports, AI suggestions) and omits note text, capture photos, transcripts, chat, events/attendees, companies, goals, outreach and recruiter data; the policy's own caveat lists four. Deleting a contact removes one row and leaves the person in `note_batches.source_text`, `contact_merges.loser_snapshot`, transcripts, `event_attendees`, `outreach_prospects` (email, phone), `ignored_people` and chat messages, while the Terms tell users to honour third parties' deletion requests "using the controls Orbit provides". *Fix:* build the export from the same category registry as deletion (one dataset per category, photos as proxied URLs); on contact delete, null or redact the structured rows tied to it and delete merge snapshots naming it; say plainly that free-text notes are not scrubbed. One day.

**B11. Config and dev-hygiene gaps.** Verified. `EVENTBRITE_CLIENT_ID/SECRET/REDIRECT_URI`, `APOLLO_API_KEY`, `TWILIO_*`, `BLOB_STORE_ID`/`VERCEL_OIDC_TOKEN` are read by code and documented nowhere (Eventbrite connect fails at OAuth start; the others silently switch features off). In development Next logs every Server Function call with its arguments, so saving a BYOK or Apollo key prints it verbatim to the terminal; the fix (`logging.serverFunctions: false`) sits only on the unmerged outreach branch (commit `4d3502a`). The `DEMO_ACCOUNT_USER_ID` comments say "reachable in production on purpose" while `env.ts` forbids it there (safe direction, stale text). `docs/performance.md` says the layout `maxDuration` is 300 (it is 60) and omits that `capture` and `imports` pages are 300. *Fix:* document the variables in `.env.example` and add the ops ones to `EXPECTED_IN_PRODUCTION`; cherry-pick the logging fix to main; fix the comments and doc. Two hours.

**B12. Production errors already in the log, and CSP still report-only.** Verified via the Vercel API (last 7 days): Apollo returned 403 "not included in your Free plan" on `/outreach/new` and "people enrichment is not available on your current plan" on `/contacts/[id]` (as recent as today), so "Contact enrichment on Orbit's credits", a listed Pro feature, does not work; the admin delete-account action throws "This account has no email on file … Delete it with scripts/ instead". `CSP_ENFORCE` is read at build time and the live header is still `Content-Security-Policy-Report-Only`. *Fix:* either buy an Apollo plan or stop advertising hosted enrichment; make the admin delete path handle email-less accounts; query `error_events` for `csp` rows and flip `CSP_ENFORCE=1` with a redeploy. Two hours plus the Apollo decision.

**B13. Scale and scheduler ceilings.** Source. Connector sync claims five connections per fifteen-minute run, serially, so continuous sync saturates at roughly ten connected calendars with no lag metric and no alert. GitHub Actions disables scheduled workflows after 60 idle days on a public repo, which would stop the sweep, the stalled-import backstop, the drain and sync at once. There are no browser tests: sign-up → onboarding → capture → save and `/upgrade` → checkout have no automated coverage. `/admin` runs six whole-table `GROUP BY user_id` aggregates on every load, on the same free compute users share. *Fix:* concurrency 4 with `Promise.allSettled` and an `oldestDueAgeMs` alert at 2 h; a calendar reminder plus runbook line for the 60-day rule (or Vercel Pro crons); a five-flow Playwright suite against previews; materialise the admin aggregates nightly. Three days.

**B14. Shared third-party quotas.** Source. Unavatar (25/day per egress IP) and Microlink are app-level and shared by every user, with process-local cooldowns invisible across Lambdas; the avatar backfill mounts on every authenticated page, so one large network drains photo lookups for everyone. Hosted Apollo spend per Pro user is uncapped (no daily bucket). The public contact form has a honeypot but sends mail on the app's Resend key. Twilio "Reply STOP" is appended but no inbound STOP webhook was found. *Fix:* a shared daily source budget in `rate_limit_buckets` plus a per-user share; `apollo.search`/`apollo.enrich` daily buckets; a small rate limit on the contact form; confirm Twilio Advanced Opt-Out is on for the number. Half a day.

## 7. Local run recipe (so the next person does not guess)

```bash
git worktree add ../orbit-audit origin/main && cd ../orbit-audit
npm ci
# demo mode, local PGlite, seeded workspace on first request:
cp .env.example .env.local   # leave DATABASE_URL and the Clerk keys unset
npm run dev
# empty-state / onboarding work: ORBIT_DEMO_DATA=off npm run dev
# to see the real sign-in surface, add the pk_test/sk_test Clerk keys and keep DATABASE_URL unset
```

Three things the README does not say: the worktree needs its own `npm ci`; `.data/pglite` may already hold fixtures from another branch (Settings → Delete data clears them and re-seeds on the next request); and changing the port breaks the Google redirect URI until the console matches.
