# Latency plan

Phase 1 deliverable: every latency cause found, with evidence, ranked; the budgets; the CI guardrails; and the decisions that are yours. Measurements and methodology are in `LATENCY_BASELINE.md`; the harness is in `latency/`.

**Stack, verified from the repo.** Next.js 16.3.8 (App Router, Turbopack, React 19.2) on Vercel Fluid Compute (`docs/performance.md`), Node 24, Drizzle 0.45 over `@neondatabase/serverless` **neon-http only** (one HTTPS request per SQL statement; no pool, no websocket; `src/db/index.ts:1-4, 4826-4834`), Neon Postgres with pgvector HNSW (1,536 dims, cosine; `src/db/index.ts:4052-4076`) plus `tsvector` and `pg_trgm` arms; PGlite locally (no pgvector). Clerk 7 (`src/proxy.ts`), streaming chat over SSE (`src/app/api/chat/route.ts`), BYOK or managed Gemini/OpenAI/Anthropic/OpenRouter keys (`src/lib/ai-access.ts`), speech via Deepgram live/batch with Whisper and Gemini fallbacks (Wispr was removed), the Constellation on `@xyflow/react`, a service worker that **caches nothing** (`public/orbit-sw.js`, notification clicks only), and integrations for Google, Microsoft, Apple CalDAV, Apollo, Resend, Twilio, Stripe, Luma, Eventbrite, Bluesky and Mastodon. No `unstable_cache`, `"use cache"`, PPR or `cacheComponents` anywhere; every app page is `force-dynamic` with `staleTimes {dynamic: 30, static: 60}`. Region is not pinned in the repo (`vercel.json` has no `regions`); the efficiency audit says functions run in `iad1` beside Neon `us-east-1`, while `.env.example` shows a `us-east-2` Neon host.

Two facts drive most of what follows. Each SQL statement is its own round trip, so **sequential depth × RTT** is the server cost of a page, and React `cache()` dedupes only inside a page render, so route handlers and Server Actions re-read `user_settings` once per helper that needs it.

## 7. The ten biggest wins, in plain language

Before/after are p50 estimates for a 5,000-contact account on a mid-range phone on 4G, from the baseline tables plus the per-finding estimates above; "after" assumes same-region Neon.

1. **Contacts page settles ~1 s sooner and the server does 50 fewer calls per visit** (#1): every avatar is currently an authenticated function call plus an uncached redirect. Before: ~50 avatar requests, list settled ~2.5–3.5 s. After: 0–2 requests, ~1.5 s.
2. **Chat answers start 2–4 s earlier on open questions** (#2, #3): the LLM rerank that often times out, default "thinking" before the first token, and a serial parse → embed → rerank chain. Before: first token ~4–7 s. After: ~1.5–2.5 s.
3. **Every page's first byte arrives 1–2 round trips sooner, and refreshes stop re-doing the shell** (#5, #11): the app layout and route handlers re-read settings and scan brand colors before anything streams. Before: TTFB ~150–300 ms. After: ~80–150 ms.
4. **Saves and searches stop rendering the page twice** (#4, #17): actions revalidate and the client refreshes again. Before: "Saved" at ~600–1,000 ms, search results ~700 ms. After: feedback at ~100 ms (optimistic), settle ~300–400 ms.
5. **Clicks stop queueing behind polls** (#6): capture/import/pulse polls run as Server Actions, one at a time per tab. Before: up to 400 ms added to any click during a poll. After: 0.
6. **Dashboard stays fast at 50,000 contacts** (#7, #8): it currently scans the whole network, decompressing every notes field and avatar blob, on every load. Before: ~0.5 s DB at 25k, growing linearly. After: < 150 ms, flat.
7. **Capture reviews land 5–30 s sooner for multi-person notes** (#10): detail batches run one after another and a successful first pass is thrown away. Before: ~25–45 s for 8 people. After: ~10–15 s.
8. **Every app page ships ~120 KB gz less JavaScript** (#12, #13): no `LazyMotion`, two navs mounted, eager panels, an italic font nobody uses on the page, a stylesheet that includes the admin console. Before: 380 KB gz dashboard + 112 KB fonts + 50 KB CSS. After: ~260 KB + 67 KB + 30 KB; usable ~0.7 s sooner on 4G.
9. **Imports show progress in under 2 s instead of after every row is staged** (#19). Before: ~20–40 s of nothing for a 20k export. After: first progress < 2 s, same throughput.
10. **Semantic search gets measured and bounded** (#20): today it runs on a global index with defaults that either return the wrong people or scan every vector a user has; nobody has ever looked at the plan. Before: unknown. After: known, and at worst an exact scan over the tenant's own rows.
